# 0006: CRDT library and document layout

Status: Accepted (sprint 0, slice 2). The layout is amended by ADR 0016 (proposed, sprint 9), after a merge harness found where it converges to the wrong thing. The note on `Y.Text` titles is withdrawn: a title merged by character reads worse than one that wins whole (`docs/research/collaboration/prior-art.md`, §1).

## Context

The plan must be a CRDT document from day one so M2's live collaboration needs no rewrite (requirements, Architecture). M2's relay only ever sees encrypted updates, so sync must work on opaque binary updates. Sprint 0 also needs every change to be undoable and to survive a reload, in a build opened from disk.

## Decision

**Yjs**, with **y-indexeddb** for local persistence and **Y.UndoManager** for undo.

Document layout (`src/store/schema.ts`), one document per scenario (ADR 0003):

- `properties`: map of property ID to a map of `kind`, `name`, `levels`, `multi`, and `values` (a map of value ID to `{label, parent, order}`).
- `items`: map of item ID to a map of `title`, `description`, `parent`, `sequence`, and `values` (a map of property ID to a **set** of value IDs, stored as map keys).
- `dependencies`: map keyed `from->to`.

The rules that make this safe for M2:

- **Multi-valued properties are sets, not arrays.** Two people tagging the same card with different components at once both land; an array would duplicate or lose one.
- **Commands write differences, not whole values.** Moving one lane of a card deletes one key and adds one. It never rewrites the item, so a concurrent edit to another field or another value survives.
- **Single-valued properties can briefly hold two values** after concurrent edits. Every reader picks the same one (lowest ID), and the next edit cleans up.
- **Only `src/store/` and `src/commands/` import Yjs.** The domain and UI see plain `Plan` snapshots; lint rules enforce both boundaries.

Undo: one `Y.UndoManager` over the three root maps, tracking only edits made through commands (so loading from storage is never undoable), with `captureTimeout: 0`, so every command is exactly one undo step. The undo history is per session; it doesn't survive a reload.

Persistence: IndexedDB database `planning-board:v<schema>:default`. Bumping `SCHEMA_VERSION` starts a fresh database instead of misreading an old layout. If IndexedDB is unavailable, the app keeps working in memory and shows a banner.

Runtime dependencies introduced: `yjs`, `y-indexeddb`.

## Alternatives

- **Automerge.** Comparable guarantees, but its WebAssembly core would make the single-file build several times larger _(priors)_, and Yjs's ecosystem (WebSocket relay, IndexedDB, undo) matches our needs directly _(recalled)_.
- **Loro.** Promising (including a native movable tree for ADR 0004), but younger, and also WebAssembly.
- **Plain JSON plus our own sync.** Every hard problem (concurrent edits, offline merge) would be ours.

## Consequences

- Browsers treat every file opened from disk as one site _(recalled; true for Chromium)_, so all downloaded builds share one saved board. A layout change must bump `SCHEMA_VERSION`, or an older build could misread a newer board.
- Item fields like `title` are plain strings for now; concurrent title edits are last-writer-wins. They become `Y.Text` when inline editing lands, if character-level merging is wanted.
- Reading a full snapshot on every change is fine at a few hundred items; revisit with incremental snapshots if plans grow much larger.
